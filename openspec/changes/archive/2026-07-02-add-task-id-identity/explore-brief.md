# Explore Brief — add-task-id-identity

## Problem

`Task.task_id: int` (`domain/model.py:197`) is a plain int at every layer. The
pre-persistence shape is a fiction: `submit_task.py:81` constructs
`Task(task_id=0, label=..., context=..., status=TO_DO)` and hands it to
`TaskRepository.insert`, whose contract explicitly says *"task_id is ignored,
generated by DB"* (`postgres.py:159`). So a `Task` with `task_id=0` is passed
around as a stand-in for "not yet persisted" — the same class represents two
states (pre- and post-persistence), and the type system can't tell them apart.

This is the **exact Task-side analog** of the `add-node-id-identity` change
(frozen proposal), which introduced `NodeId` + `NewNode`/`Node` split for
`yascheduler_nodes`. That proposal even calls out the inconsistency: it notes
`TaskRepository.insert(task) -> Task` as the consistency anchor its own
`NodeRepository.insert` will mirror — yet `Task` itself still carries the
`task_id=0` fiction. This change closes that gap and makes `Task` consistent
with the `Node`/`NewNode`/`NodeId` pattern.

Unlike the Node change, **no DB migration is needed**: `yascheduler_tasks.task_id
SERIAL PRIMARY KEY` already exists, and `task/insert.sql` already ends with
`RETURNING task_id, label, ip, status, metadata`. So this is a pure
domain/application-layer change (no `sql-queries` or `db-migrations` deltas).

## Rejected alternatives

- **`Task.task_id: int | None = None` (nullable)** — every consumer must handle
  `None`; uncomfortable and leaky. Rejected in favor of a `NewTask`
  (pre-persistence) / `Task` (post-persistence, always carries `TaskId`) split,
  so the type system makes "task not yet persisted" unrepresentable as a `Task`.
  (Same rationale as Node's rejection of `node_id: int | None`.)
- **`TaskId = typing.NewType('TaskId', int)`** — erased to `int` at runtime, no
  validation, no methods. Rejected in favor of a frozen dataclass value object
  `TaskId(value: int)`. (Same as Node.)
- **`TaskId` as an `int` subclass** — defeats value-object ergonomics and the
  explicit "frozen dataclass with value: int" design. Rejected. (Same as Node.)
- **Scope A (persistence-identity only: events/exceptions/repo-methods stay
  `int`)** — leaves the domain internally inconsistent (`Task.task_id: TaskId`
  but `DomainEvent.task_id: int`, `TaskAlreadyAllocatedError(task_id: int)`),
  forcing `.value` extractions scattered across `Task.with_event` and every
  lifecycle method. Rejected in favor of Scope B: the domain is type-safe
  end-to-end, and the `int`/`TaskId` boundary lives in exactly one place — the
  public `Yascheduler` facade.
- **Scope C (TaskId on the public `Yascheduler` facade)** — BREAKING to the
  frozen public API (`queue_get_task(task_id: int)`,
  `queue_submit_task(...) -> int`). Rejected — violates the public-interface
  stability rule.
- **Keep `list_ids_by_ip_and_status -> list[int]` and
  `list_by_jobs(job_ids: list[int])` as a "batch API carve-out"** — rejected.
  `list_ids_by_ip_and_status` feeds `update_status(task_id: TaskId)` in
  `yasetnode`; keeping its return `list[int]` would force a `TaskId(i)` wrap in
  the CLI loop. `list_by_jobs` is driven by the facade (`jobs=[int]`), but the
  facade is already the marshalling boundary, so converting `[TaskId(i) for i in
  jobs]` at the facade edge is consistent with the boundary story. So **all
  repository methods take/return `TaskId`**; the facade is the sole `int`
  boundary, in both directions.
- **Keep use-case entry points `allocate_task(task_id: int)` /
  `consume_task(task_id: int)`** — rejected. The orchestrator reads task ids
  from `list_by_status -> list[Task]` (i.e. `Task.task_id: TaskId`), so the use
  cases naturally receive `TaskId` already; converting back to `int` at the
  use-case boundary would re-introduce the inconsistency Scope B avoids. Use
  cases take `TaskId`.
- **Drop `allocated_ip` from `NewTask`** — the sole construction site
  (`submit_task`) leaves it default-`None`, so omitting it is *possible*. But
  `insert.sql` writes `ip = :ip` and `Task` carries it; symmetry with `NewNode`
  (which carries all non-identity fields) argues for keeping it with default
  `None`. Rejected the omission.
- **Put lifecycle methods on `NewTask`** — rejected. `NewTask` is
  pre-persistence; "allocate"/"mark running"/"complete" are nonsensical on a
  task with no id. All lifecycle methods stay on `Task`. `NewTask` is a pure
  data carrier (fields only, no methods).

## Final approach (decisions locked with user)

| Axis | Decision |
|---|---|
| Scope | **B** — domain-internal type-safety end-to-end; the public `Yascheduler` facade is the sole `int`/`TaskId` boundary (both directions). |
| `TaskId` | `@dataclass(frozen=True) class TaskId: value: int` in `yascheduler/domain/model.py`. `__post_init__` asserts `value > 0` (SERIAL ≥ 1), raising `ValueError`. `__str__` returns `str(self.value)`. Hashable (frozen). NOT equal to bare `int` (`TaskId(5) == 5` is `False`). Direct copy of `NodeId`. |
| `NewTask` | frozen dataclass: `label: str`, `context: TaskContext`, `status: TaskStatus = TaskStatus.TO_DO`, `allocated_ip: str \| None = None`. **No** `task_id`, **no** `_events`. Pure data carrier — no lifecycle methods. |
| `Task` | frozen dataclass: same fields + `task_id: TaskId` (first field, identity first) + `_events: tuple[DomainEvent, ...] = ()` (repr=False). Lifecycle methods (`allocate_to`, `mark_running`, `complete`, `fail`, `reject`, `with_context`, `with_event`, `pull_events`, `record_event`) unchanged in behavior. |
| Sole NewTask→Task conversion | `TaskRepository.insert(new_task: NewTask) -> Task` (the method that persists and receives the generated id). Mirrors `NodeRepository.insert`. |
| Events | `DomainEvent.task_id: TaskId` + all 5 subclasses (`TaskCreated`/`TaskAllocated`/`TaskCompleted`/`TaskFailed`/`TaskAbandoned`). `Task.with_event` constructs with `task_id=self.task_id` (already `TaskId` — no `.value` needed). |
| Exceptions | domain `TaskAlreadyAllocatedError`, `TaskNotAllocatedError`, `TaskNotTodoError`, `TaskNotRunningError`, `NoCompatibleNodeError`, `CloudCapacityExhaustedError` + infra `TaskRowNotFoundError` — all take `task_id: TaskId`. `f"task {task_id} ..."` renders cleanly via `__str__`. |
| `TaskRepository` (Protocol + Postgres impl) | `insert(new_task: NewTask) -> Task`; `get(task_id: TaskId) -> Task \| None`; `save(task: Task) -> None` (unchanged shape — `task.task_id.value` to SQL); `update_status(task_id: TaskId, status) -> None`; `list_ids_by_ip_and_status(...) -> list[TaskId]`; `list_by_jobs(job_ids: list[TaskId]) -> list[Task]`. DB params pass `task_id.value` (pg8000 can't adapt a dataclass). |
| `_row_to_task` | wraps `TaskId(int(row["task_id"]))`. |
| `submit_task` use case | return type `int -> TaskId`. Body: construct `NewTask(label, context)` → `insert` → `Task` → `with_context`/`with_event`/`save` → return `task.task_id` (`TaskId`). |
| `allocate_task` / `consume_task` use cases | entry param `task_id: int -> task_id: TaskId`. |
| Orchestrator | reads `Task.task_id: TaskId` from `list_by_status` and feeds `allocate_task`/`consume_task` — `TaskId` end-to-end, no conversion. Tracker keys become `TaskId` (internal). |
| Public `Yascheduler` facade | UNCHANGED signatures (`queue_submit_task(...) -> int`, `queue_get_task(task_id: int)`, `queue_get_tasks(jobs: list[int])`). The facade is the int/TaskId marshalling layer: on `queue_get_task`/`queue_get_tasks` input, `TaskId(int)`-wrap; on `queue_submit_task`/`queue_get_task(s)` output, extract `.value`. |
| `yanodes` / `yastatus` / `yasubmit` CLIs | `yasubmit` prints `str(task_id)` (works via `__str__`, no change). `yastatus` text renderers (`_render_default` f-string, `_render_info` `.format`) work via `__str__`, no change; BUT `yastatus`'s `_render_json` does `"task_id": task.task_id` then `json.dumps` — `json.dumps` does NOT call `__str__` and would raise `TypeError` on a `TaskId`, so it MUST become `task.task_id.value`. `yastatus`'s `_query_tasks` passes `args.jobs` (`list[int]`) to `list_by_jobs` — must wrap `[TaskId(j) for j in args.jobs]` (CLI-internal, same as facade). `yanodes` carries `TaskId` through `_NodeView` (mirroring Node's `NodeId`), extracts `.value` only at the JSON renderer. |
| `yasetnode` | `list_ids_by_ip_and_status -> list[TaskId]` feeds `update_status(task_id: TaskId)` directly — no conversion in the loop. |
| DB migration | NONE. `task_id SERIAL PRIMARY KEY` already exists; `insert.sql` already has `RETURNING task_id`. |
| SQL queries | NONE. No query file changes. |
| Webhook handler | `infra/notifier/webhook.py:86` constructs `WebhookPayload(task_id=event.task_id, status=status.value, custom_params=...)` and `_send_webhook` serializes via `asdict(payload)` into the HTTP POST body (`webhook.py:112`). Since `event.task_id` becomes `TaskId` (Scope B), line 86 MUST extract `.value`: `task_id=event.task_id.value` (otherwise `asdict` recurses into the `TaskId` dataclass and the body becomes `{"task_id": {"value": 42}, ...}` instead of `{"task_id": 42, ...}` — a runtime shape break). `WebhookPayload.task_id: int` (line 48) stays `int` (the correct target type). So the webhook handler IS in scope (one `.value` extraction); the wire payload shape is preserved. Spec scenarios update event-construction literals to `TaskId(42)`. |

## Cross-module data flows

- **Submit (CLI / facade):** `yasubmit "label" ... engine` → `submit_task(label,
  metadata, engine_name, ...)` builds `NewTask(label=label, context=context)`
  (status defaults TO_DO, allocated_ip defaults None) →
  `uow.tasks.insert(new_task)` runs `task/insert.sql ... RETURNING task_id` →
  `Task(task_id=TaskId(int(row["task_id"])), ...)` → `with_context(remote_folder
  based on task.task_id)` → `with_event(TaskCreated, ...)` → `uow.tasks.save(task)`
  → `commit` → returns `task.task_id` (`TaskId`). The CLI prints `str(TaskId)`
  → bare integer. The facade `queue_submit_task` wraps `submit_task` and
  returns `task_id.value` (`int`) to keep the public API `-> int`.
- **Allocate:** orchestrator → `list_by_status({TO_DO})` → `[Task]` (each carries
  `TaskId`) → `allocate_task(task.task_id: TaskId, ...)` →
  `uow.tasks.get(task_id: TaskId)` → `Task` → `allocate_to(ip)` →
  `with_event(TaskAllocated, ...)` → `save(task)` (SQL gets `task.task_id.value`).
- **Consume:** `consume_task(task_id: TaskId, ...)` →
  `uow.tasks.get(task_id: TaskId)` → `Task` → download →
  `complete()/fail()` → `with_event(TaskCompleted/TaskFailed, ...)` →
  `save(task)` → tracker keys `TaskId`. `download_outputs(..., task_id=
  task.task_id)` — SSH ops uses it for logging/folder naming; `TaskId.__str__`
  handles rendering, no `.value` needed.
- **Facade read:** `queue_get_task(task_id: int)` → facade wraps
  `TaskId(task_id)` → `list_by_jobs([TaskId(task_id)])` (or `get(TaskId(...))`)
  → `Task` → facade builds `{"task_id": task.task_id.value, "label": ...,
  "ip": ..., "status": ..., "metadata": ...}` (`int` to the public API).
- **yasetnode remove-node:** `list_ids_by_ip_and_status(node.ip, DONE) -> list[
  TaskId]` → loop `update_status(task_id: TaskId, DONE)` directly (no
  conversion).

## Open questions

All resolved (see Decisions table above). The scope (B), the batch-API choice
(all TaskId, no carve-out), the NewTask shape (with `allocated_ip`), and the
facade-as-sole-boundary are all locked.
