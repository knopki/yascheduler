## Context

`PostgresTaskRepository.save()` and `.update_status()` execute bare
`UPDATE ... WHERE task_id = :task_id` statements (`sql/task/upsert.sql`,
`sql/task/update_status.sql`) with no `RETURNING` clause and no row-count
check. `save()`'s contract labels this an "upsert by task_id" — false, since
there is no `INSERT ... ON CONFLICT` and no row-count detection. When no row
matches `task_id`, the UPDATE affects 0 rows silently: no error, no log,
and `save()` still appends the task to the UoW's `_saved_tasks` list as if
it were persisted, after which `publish_events` would dispatch events for a
task whose DB row was never updated.

All five current `save()` call sites and the single `update_status()` call
site operate on rows they just loaded via `get()`/`insert()` (with
None-checks), so no live data loss occurs today. The danger is latent: the
contract lies, and one live path — the orchestrator's task-abandon block at
`orchestrator.py:440` — races the row's lifetime and currently silent-no-ops
on the race.

Constraint: `task_id` is `SERIAL PRIMARY KEY` (`schema.sql:11`), generated by
the DB at `insert()` time via `RETURNING task_id`. A true
`INSERT ... ON CONFLICT (task_id) DO UPDATE` "upsert" is incompatible with
this — `save(Task(task_id=0))` would insert a garbage row with `task_id=0`.
The `insert()`/`save()` split is load-bearing and preserved.

## Goals / Non-Goals

**Goals:**
- Make the silent 0-row outcome of `save()` and `update_status()` loud: raise
  a programming-error exception when the targeted row does not exist.
- Stop lying in the contract: rename `upsert.sql` → `update_by_id.sql` and
  fix the `save()` PURPOSE/docstring to describe a partial update with a
  row-existence precondition.
- Prevent the orchestrator's task-abandon race from silently killing a
  consumer worker when the new raise is introduced, by wrapping the consumer
  worker symmetrically to the existing allocator-consumer wrap.
- Keep the public `TaskRepository` port signatures unchanged
  (`save`/`update_status` stay `async def ... -> None`); the raise is a new
  failure mode on a path that was previously silently broken, not a
  signature break.

**Non-Goals:**
- Merging `insert()` + `save()` into a single round-trip in `submit_task`
  (architectural — `remote_folder` depends on the SERIAL-generated
  `task_id`, so it cannot be known before `insert()`).
- Making `datetime.now()` in `submit_task` timezone-aware (separate
  proposal).
- Removing the dead `sql/task/update_meta.sql` file (separate cleanup; no
  `load_query` references it today).
- Changing the `TaskRepository` Protocol signatures.
- Catching `TaskRowNotFoundError` anywhere in application code — it is a
  programming error signaling a contract violation; the orchestrator worker
  wrap catches the broader `Exception` (logging and continuing), not this
  specific type.

## Decisions

### Decision 1: Detect 0-row outcome via `RETURNING task_id`, raise — not via `rowcount`

pg8000's `Connection.run` returns the result rows; `_run` in
`postgres.py:52` already returns `list[dict]` keyed by column name. Adding
`RETURNING task_id` to the UPDATE statements makes a 0-row outcome
observable as an empty list, with zero new pg8000 API surface. The
alternative — reading `Connection.rowcount` — would require reaching into
pg8000 internals not currently used and would be less consistent with the
existing `_run`-returns-rows pattern.

**Alternatives considered:**
- `Connection.rowcount`: rejected — new pg8000 surface, inconsistent with
  the existing `_run` shape.
- `INSERT ... ON CONFLICT (task_id) DO UPDATE` (real upsert): rejected —
  incompatible with SERIAL `task_id`; `save(Task(task_id=0))` would create a
  garbage row.
- `save()` swallows the 0-row and logs: rejected — the exception would
  exist on paper but never fire, violating its own contract.

### Decision 2: `TaskRowNotFoundError(RuntimeError)`, sibling of `UnitOfWorkNotInitializedError`

The exception lives in `yascheduler/infra/persistence/exceptions.py`, the
persistence-adapter exception module, NOT in
`yascheduler/domain/exceptions.py`. Rationale: the existing domain
`Task*Error` hierarchy (`TaskNotTodoError`, `TaskNotRunningError`, ...)
expresses **business-rule** violations that the domain validates and that
use cases may catch and recover from. "The row you said exists does not"
is a **contract precondition violation** at the repository boundary — a
programming error, not a business rule. Its sibling
`UnitOfWorkNotInitializedError(RuntimeError)` expresses the same nature
(UoW API used outside its `async with` contract) and inherits from
`RuntimeError` for the same reason (not catchable as a domain error,
backward-compatible with `except RuntimeError`). `TaskRowNotFoundError`
follows that precedent exactly.

**Constructor:** `__init__(self, task_id: int)` storing `self.task_id` and
calling `super().__init__(f"task row not found for task_id={task_id}")`.
Mirrors `TaskNotRunningError.__init__` shape but inherits from `RuntimeError`.

Callers SHALL NOT catch `TaskRowNotFoundError` to implement recovery logic.
The orchestrator worker wrap catches `Exception` (broader) and logs; it
does not single out this type.

### Decision 3: Raise BEFORE `_saved_tasks.append` in `save()`

`save()` today appends to `_saved_tasks` unconditionally after the UPDATE.
Under the new behavior, the row-count check raises before the append line.
This ordering is load-bearing for race correctness in the orchestrator
abandon path: if the raise fired after the append, the orphaned task would
linger in `_saved_tasks` and `publish_events` would dispatch a
`TaskAbandoned` event for a task whose DB row was never updated — a
DB/event desync. Raising first guarantees the task never enters
`_saved_tasks`; `__aexit__`'s rollback path then `ROLLBACK`s (a no-op on
0-row UPDATE) and `_saved_tasks.clear()` is a no-op on an already-empty
list. The `TaskAbandoned` event constructed via `with_event` lives only on
the in-memory `task` instance and is correctly discarded.

### Decision 4: Wrap the consumer worker, not the consumer function

The orchestrator's `_create_producer_consumers` defines an inner
`worker()` coroutine (`orchestrator.py:580-586`) with bare
`try: await consumer(msg)` / `finally: queue.item_done(msg)` — no `except`.
A raise out of `consumer(msg)` propagates to the worker `asyncio.Task`,
which dies silently (no `.result()` awaited in the normal loop; the
`except CancelledError` drain only awaits workers at shutdown). Under the
new raise, the orchestrator:440 race would silently lose a consumer,
reducing queue throughput.

The fix wraps the `try` in `try/except Exception` inside `worker()`,
logging the error, and preserving the `finally: queue.item_done(msg)` so
the queue item is still dequeued. This is symmetric to the existing
producer-error resilience requirement (`orchestrator` spec, "Producer error
resilience") and to the allocator-consumer's `try/except Exception` at
`orchestrator.py:386-394`. The allocator wraps at the consumer-function
level (`_allocator_consumer`); the consume path wraps at the worker level
because `_task_consumer_consumer` is the consumer callable passed into
`_create_producer_consumers` and the worker is the place where an
unhandled raise would kill the task. Both achieve the same effect: a
consumer exception is logged, the loop continues.

`CancelledError` (a `BaseException` since 3.8, not `Exception`) propagates
past the new `except Exception` to the existing `except CancelledError`
drain path, preserving graceful shutdown. This mirrors the producer
resilience spec exactly.

### Decision 5: Rename `upsert.sql` → `update_by_id.sql`

The file name `upsert.sql` is itself misleading. Renaming to
`update_by_id.sql` aligns with the existing `get_by_id.sql` naming
convention (entity-keyed operation names) and accurately describes the
statement. `load_query("task/upsert")` becomes
`load_query("task/update_by_id")` in `save()`. No other code references
the old name.

## Risks / Trade-offs

- **[Risk] New raise on previously-silent path could surprise a caller
  that silently relied on the no-op.** → Mitigation: all 5 `save()` and 1
  `update_status()` call sites were audited; all operate on rows they just
  loaded or inserted (with None-checks), so the raise never fires on
  correct existing code. The only new live raise site is the
  orchestrator:440 race, which is exactly the bug we want to make loud.
- **[Risk] Worker wrap masks the new exception instead of surfacing it.**
  → Mitigation: the wrap logs at `error` level (visible), the worker
  continues (no throughput loss), and the queue item is dequeued
  (`finally`). The race self-heals: the producer's next
  `list_by_status({RUNNING})` cycle will not yield a genuinely-deleted
  task_id, so the consume loop stops re-entering the abandon block for it.
  If the row was not actually deleted (transient anomaly), the next
  cycle's `save()` succeeds. A worker that silently died (today's
  behavior under any consumer exception) is strictly worse than a logged
  error with continued operation.
- **[Trade-off] `RETURNING task_id` adds a tiny per-UPDATE overhead.** The
  returned row is small (one int column) and the alternative (no
  detection) is the bug being fixed. Acceptable.
- **[Trade-off] Two artifacts touch SQL files** (`update_by_id.sql` rename +
  `update_status.sql` edit) — slightly wider than a single-file fix, but
  both are the same class of bug and fixing only one leaves the sibling
  footgun live. Acceptable per the brief's decision to include
  `update_status`.

## Migration Plan

No DB schema migration: `yascheduler_tasks` schema is unchanged (the
`UPDATE ... RETURNING task_id` works on the existing `task_id` column). No
data migration. Rollback is a code revert (delete `RETURNING`, restore
`upsert.sql` name, remove the exception and the worker wrap). The change
is backward-compatible at the public port level (signatures unchanged); the
new raise is a new failure mode on a previously-silently-broken path, not
a signature break.
