# Explore Brief — fix-save-silent-zero-rows

## Problem (confirmed by code read)

`yascheduler/infra/persistence/sql/task/upsert.sql` is a bare `UPDATE ... WHERE
task_id = :task_id` with no `RETURNING`. `PostgresTaskRepository.save()`
(`postgres.py:103`) ignores the row count returned by `_run` and appends the
task to `_saved_tasks` unconditionally. If no row matches `task_id`, the
UPDATE affects 0 rows **silently**: no error, no log, no signal to the caller.
The contract (`save` PURPOSE / docstring) calls this an "upsert", which is
false — it is a partial update with a hidden precondition (row must exist).

`sibling: update_status.sql` (bare `UPDATE ... SET status`) +
`PostgresTaskRepository.update_status()` (`postgres.py:124`) has the identical
silent-zero-rows shape. Same class of bug.

### Blast radius today (all 5 save() callers verified safe)

- `submit_task.py:93` — preceded by `insert()` (row guaranteed). Safe.
- `allocate_task.py:92` (`_validate_engine`) — preceded by `get()` with
  None-check at `allocate_task:455-457`. Safe.
- `allocate_task.py:141` (`_try_start_on_machine`) — task from `get()`.
  Safe.
- `consume_task.py:180` (`_finalize_task`) — task from `get()` with
  None-check at `consume_task:221-226`. Safe.
- `orchestrator.py:440` (`_task_consumer_consumer` MACHINE_GONE block) —
  task from `msg.payload` (loaded by producer via `list_by_status`). **Race
  window**: row could be deleted between producer enqueue and consumer
  `save()`. Today silent 0-row. Narrow but real.

`update_status()` caller: `manage_node.py:204` inside a loop over
`list_ids_by_ip_and_status` in the same UoW. Safe today.

### Latent danger (the actual motivation)

The contract lies. A future author reading "upsert by task_id" will reasonably
call `save(Task(task_id=0, ...))` on a fresh task expecting an INSERT, get a
silent 0-row no-op, and lose data. The name + contract are an active
footgun, not a passive typo. The orchestrator:440 race is a real (if narrow)
live instance of the silent loss.

## Rejected alternatives

- **B — real `INSERT ... ON CONFLICT (task_id) DO UPDATE`**: semantically
  incompatible. `task_id` is `SERIAL PRIMARY KEY` (`schema.sql:11`),
  generated by the DB at `insert()` time. `save(Task(task_id=0))` would
  insert a row with `task_id=0` (SERIAL skips explicit 0) — garbage ID,
  breaks the `insert()`/`save()` split. Rejected.

- **C alone — RETURNING + raise, no rename**: fixes the footgun but leaves
  the misleading name/contract. Rejected in favor of D.

- **save() swallows and logs on 0 rows**: violates save()'s own contract
  (the exception exists on paper but never fires). Worst of both worlds.
  Rejected.

## Final approach — D (rename + detect-and-raise) + consumer worker wrap

1. Rename `upsert.sql` → `update_by_id.sql`; add `RETURNING task_id`.
2. `update_status.sql` gets the same `RETURNING task_id` treatment.
3. `save()` and `update_status()` check the returned row count; raise
   `TaskRowNotFoundError` on 0 rows.
4. New exception `TaskRowNotFoundError(RuntimeError)` in
   `yascheduler/infra/persistence/exceptions.py`, sibling to
   `UnitOfWorkNotInitializedError`. NOT a domain exception (not under
   `TaskError(DomainError)`): it is a programming-error / contract
   precondition violation, not a business rule. Unrecoverable; callers
   shall NOT catch it.
5. Wrap the orchestrator consumer worker (`orchestrator.py:583-586`,
   `_create_producer_consumers` inner `worker()`) in `try/except Exception`
   symmetric to the allocator path (`orchestrator.py:386-394`). Today the
   worker has bare `try/finally` (no `except`): a raise out of `consumer(msg)`
   kills the worker task silently. Under D, the orchestrator:440 race would
   raise `TaskRowNotFoundError` and silently lose a consumer. The wrap logs
   the error and lets the worker continue. `finally: queue.item_done(msg)`
   is preserved (item still dequeued on error). This is fixing a
   pre-existing asymmetry exposed by the new guardrail, not adding a new
   feature.
6. Knowledge graph: add `class-TaskRowNotFoundError` annotation under
   `M-PERSISTENCE-EXCEPTIONS`; add `CrossLink` from `M-PERSISTENCE-POSTGRES`
   to `M-PERSISTENCE-EXCEPTIONS` (repos raise persistence exceptions, not
   just UoW).

### Race resolution semantics (scenario i — confirmed by trace)

Under D, orchestrator:440 race: `save()` raises `TaskRowNotFoundError` BEFORE
the `_saved_tasks.append(task)` line in `save()` (raise is on the row-count
check, append is after). So the task is never added to `_saved_tasks`.
`__aexit__` sees the exception, calls `rollback()` which does `ROLLBACK` (0
rows were changed anyway) and `self._saved_tasks.clear()` (already empty).
The `TaskAbandoned` event lives only on the in-memory `task` instance
(added via `with_event` at line 438); it never reaches `publish_events`.
**Event is silently dropped — correct: the task no longer exists, the event
refers to a non-existent entity, no one to publish to.** Self-heals:
producer's `list_by_status({RUNNING})` will no longer yield the deleted
task_id next cycle, so the consume loop stops re-entering the abandon
block for it. If the row was NOT actually deleted (transient anomaly), the
next cycle's `save()` succeeds.

## Cross-module data flows

- `submit_task` → `uow.tasks.insert` (gets task_id) → compute remote_folder
  → `uow.tasks.save` (now safe under D: row guaranteed by insert). Two
  round-trips in one UoW — architectural (task_id from SERIAL, remote_folder
  depends on it). Not in scope to change. The tz-aware `datetime.now()`
  question in submit_task is explicitly OUT OF SCOPE for this change.
- `allocate_task._validate_engine` → `get` (None-check) → `save`. Safe.
- `allocate_task._try_start_on_machine` → `save`. Safe.
- `consume_task._finalize_task` → `save`. Safe.
- `orchestrator._task_consumer_consumer` MACHINE_GONE → `save` (race
  possible). Worker wrap handles the raise.
- `manage_node._remove_node_hard` → `list_ids_by_ip_and_status` → loop
  `update_status`. Safe (same UoW).

## Test strategy

- Unit (`tests/unit/`): existing `conftest.py:75` mocks
  `uow.tasks.save = AsyncMock()` — unaffected (mock doesn't raise). No new
  unit tests needed for the mock-based use-case tests; the raise path is a
  repository-internal precondition, tested at integration level.
- Integration (`tests/integration/`, per `test-db-integration` spec):
  - `save()` with non-existent task_id raises `TaskRowNotFoundError`.
  - `update_status()` with non-existent task_id raises
    `TaskRowNotFoundError`.
  - Existing 4 `save()` integration tests (test_persistence_adapter.py:277,
    298, 343, 374) continue to pass (rows exist).
- Orchestrator unit (`tests/unit/test_application_orchestrator.py`): add a
  test that a consumer raising `TaskRowNotFoundError` is logged and the
  worker continues (does not crash the loop). Mirrors the
  `test_producer_exception_continues_loop` pattern
  (`test_orchestrator_producer_resilience.py:184`) but for the consumer
  side.
