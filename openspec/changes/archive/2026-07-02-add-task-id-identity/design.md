## Context

`Task.task_id: int` (`domain/model.py:197`) is a plain int at every layer, and the
pre-persistence shape is a fiction. The single production construction site is
`application/submit_task.py:81`:

```python
task = Task(task_id=0, label=label, context=context, status=TaskStatus.TO_DO)
```

This `Task(task_id=0, ...)` is handed to `TaskRepository.insert`, whose contract
explicitly says *"task_id is ignored, generated by DB"*
(`infra/persistence/postgres.py:159`). `insert` runs `task/insert.sql` — which
**already** ends with `RETURNING task_id, label, ip, status, metadata` — and
returns a `Task` with the real DB-generated id. So the same `Task` class
represents two states (pre- and post-persistence), and the `task_id=0` sentinel
is a load-bearing magic value: ~30+ integration-test sites construct
`Task(task_id=0, ...)` to feed `insert`, and every reader of `Task.task_id`
silently accepts a `0` that means "not real yet".

This is the **exact Task-side analog of the `add-node-id-identity` change**
(frozen proposal), which introduced `NodeId` + `NewNode`/`Node` for
`yascheduler_nodes`. That proposal even cites `TaskRepository.insert(task) ->
Task` as the consistency anchor its own `NodeRepository.insert` mirrors — yet
`Task` itself still carries the `task_id=0` fiction. This change closes that gap.

**Key difference from the Node change: no DB work.** `yascheduler_tasks.task_id
SERIAL PRIMARY KEY` already exists, and `task/insert.sql` already has `RETURNING
task_id`. So this is a pure domain/application-layer change — no migration, no
SQL query edits, no `sql-queries` or `db-migrations` deltas.

The chosen scope is **B**: the domain is type-safe end-to-end (`TaskId` on
`Task`, events, exceptions, and every `TaskRepository` method), and the public
`Yascheduler` facade is the **sole** `int`/`TaskId` boundary (both directions).

## Design

### The identity problem and the persistence-state split

The `task_id=0` fiction exists because `Task` represents two states with one
class. A nullable `task_id: int | None` was rejected (it forces every consumer
to handle `None`). Instead the type system expresses persistence state with a
`NewTask` (pre-persistence, no identity) / `Task` (post-persistence, always
carries `TaskId`) split — the same pattern the frozen `add-node-id-identity`
change chose for `Node`/`NewNode`/`NodeId`. The conversion `NewTask → Task`
happens in exactly one place: `TaskRepository.insert`.

Scope B (chosen over Scope A) means `TaskId` propagates end-to-end inside the
domain: events and exceptions carry `TaskId`, and every `TaskRepository` method
takes/returns `TaskId`. This avoids scattering `.value` extractions across
`Task.with_event` and the lifecycle methods (which Scope A would require). The
**sole** `int`/`TaskId` boundary is the public `Yascheduler` facade — one
marshalling layer, in both directions.

### Domain model: `NewTask` / `Task` / `TaskId`

```python
@dataclass(frozen=True)
class TaskId:
    value: int
    def __post_init__(self) -> None:
        if self.value <= 0:
            raise ValueError(f"TaskId must be > 0, got {self.value}")
    def __str__(self) -> str:
        return str(self.value)

@dataclass(frozen=True)
class NewTask:
    """Pre-persistence task record — no identity yet. Pure data carrier."""
    label: str
    context: TaskContext
    status: TaskStatus = TaskStatus.TO_DO
    allocated_ip: str | None = None

@dataclass(frozen=True)
class Task:
    """Post-persistence task record — always carries its identity."""
    task_id: TaskId
    label: str
    context: TaskContext
    status: TaskStatus = TaskStatus.TO_DO
    allocated_ip: str | None = None
    _events: tuple[DomainEvent, ...] = field(default=(), repr=False)
    # lifecycle methods unchanged in behavior
```

`task_id` is the **first** field of `Task` (identity first). `NewTask` mirrors
the non-`task_id`/non-`_events` fields with identical defaults. `NewTask` is a
**pure data carrier**: it has no lifecycle methods (`allocate_to`/`mark_running`/
`complete`/etc. are nonsensical on an unpersisted task and stay on `Task`) and
no `_events` (events are collected on the persisted `Task` after `insert`).

Field order for `Task` puts `task_id` before `label`/`context` (both required,
no defaults) — valid for dataclasses since `task_id` has no default and precedes
other required fields; the defaulted fields follow. Construction sites use
keyword args (verified at `submit_task.py:81`, `postgres.py:235`), so reordering
is source-compatible.

The conversion `NewTask → Task` happens in **exactly one place**:
`TaskRepository.insert`. No other code constructs a `Task` from a `NewTask`; a
`Task` only ever comes from the database (via `_row_to_task`) or from `insert`'s
return. This makes "don't construct a `Task` without a real id" structural
rather than convention-based — the `task_id=0` sentinel becomes unrepresentable
(`Task`'s `task_id: TaskId` field is required, and `TaskId(0)` raises).

`TaskId` is a frozen dataclass, not `typing.NewType` (erases to `int` at runtime,
no validation/methods) and not an `int` subclass (defeats value-object
ergonomics). `__post_init__` enforces `value > 0` (SERIAL starts at 1), catching
accidental `0`/negative ids at construction. `__str__` returns the bare integer
string so CLI rendering and logging produce `5`, not `TaskId(value=5)`.
`TaskId(5) == 5` is `False` — the type-safety point: callers cannot accidentally
mix a `TaskId` with an unrelated `int`.

### `TaskId` at boundaries

Because `TaskId` is intentionally not an `int`, every external boundary must
handle the unwrap explicitly:

- **pg8000 params** — `task/get_by_id.sql`, `update_by_id.sql`,
  `update_status.sql` all use `WHERE task_id = :task_id`;
  `PostgresTaskRepository.get`/`update_status`/`save` pass
  `task_id=task_id.value` / `task_id=task.task_id.value` (pg8000 cannot adapt a
  dataclass). Same approach as `add-node-id-identity`'s `get_by_id(node_id)`.
- **DB read** — `_row_to_task` wraps `TaskId(int(row["task_id"]))`. pg8000
  returns `task_id` as a Python `int`.
- **JSON serialization** — `json.dumps` does NOT call `__str__`; a frozen
  dataclass raises `TypeError: Object of type TaskId is not JSON serializable`.
  Every site that emits `task_id` into a JSON payload MUST extract `.value`:
  - `yastatus` `_render_json` (`check_status.py:181`): `"task_id":
    task.task_id.value`.
  - `yanodes` JSON renderer (`show_nodes.py:241`): `{"task_id": r.task_id.value,
    ...}`.
  - `Yascheduler._task_to_dict` (`client.py:89`): `"task_id": t.task_id.value`
    (the public dict keeps `int`).
- **`asdict` serialization (webhook)** — `dataclasses.asdict` DOES recurse into
  nested dataclasses but does NOT call `__str__`; it would turn
  `WebhookPayload(task_id=TaskId(42), ...)` into `{"task_id": {"value": 42},
  ...}` — a wire-shape break (not a `TypeError`, but a silently-wrong payload).
  `infra/notifier/webhook.py:86` MUST extract `.value`:
  `WebhookPayload(task_id=event.task_id.value, ...)`. `WebhookPayload.task_id:
  int` (`webhook.py:48`) stays `int` (the correct target type). `_send_webhook`
  serializes via `asdict(payload)` into the HTTP POST body (`webhook.py:112`);
  the handler is wired for all 5 event types at `entrypoints/di.py:120`.
- **CLI text rendering / logging** — `str(task_id)` / f-`{task_id}` /
  `.format(task_id)` render via `__str__`. These sites are unchanged:
  - `yasubmit` `print(str(task_id))` (`submit.py:173`).
  - `yastatus` `_render_default` f-string (line 145) and `_render_info` `.format`
    (line 159).
  - `yanodes` table renderer `str(row.task_id)` (`show_nodes.py:205`).
  - Use-case `logger.info("task_id=%s ...", task.task_id)` calls — `%s` calls
    `__str__`.
  - `download_outputs(..., task_id=task.task_id)` (SSH ops, logging/folder
    naming) — `__str__` handles it.

This split (text renderers via `__str__`, JSON via `.value`) is the critical
distinction: a `.value` extraction missed at a JSON site is a **runtime crash**
(`TypeError`), not a cosmetic issue. The `yastatus _render_json` site is the
non-obvious one (the proposal's first review missed it; it was caught in round
2).

### Events and exceptions: `TaskId` propagates (Scope B)

`DomainEvent.task_id: int -> task_id: TaskId` and all 5 subclasses inherit the
new type. `Task.with_event` already constructs events with
`task_id=self.task_id` — after the change `self.task_id` is a `TaskId`, so no
`.value` extraction is needed; the event just carries the `TaskId`. Events are
constructed only from `Task.with_event` (verified: no external call site
constructs a `DomainEvent` subclass with a bare `task_id` except in tests, which
update to `TaskId(42)`).

The 7 task-keyed exceptions all take `task_id: TaskId` (was `int`). Their
`f"task {task_id} ..."` messages render via `TaskId.__str__` → bare integer, so
the messages are unchanged in appearance (`"task 42 is already allocated to a
node"`). The exceptions store the `TaskId` on `self.task_id`; existing scenarios
that assert `e.task_id == 42` update to `e.task_id == TaskId(42)`.

`event.task_id` DOES cross to the webhook body: `webhook_handler`
(`infra/notifier/webhook.py:74`) builds `WebhookPayload(task_id=event.task_id,
...)` (line 86) and `_send_webhook` serializes via `asdict(payload)` (line 112).
So `webhook.py:86` is a `.value` extraction site (`task_id=event.task_id.value`)
— otherwise `asdict` recurses into `TaskId` and the body becomes
`{"task_id": {"value": 42}, ...}`. The webhook handler's spec scenarios update
their event-construction literals to `TaskId(42)` for consistency, and the
handler gains the one-line `.value` extraction; the wire payload shape is
preserved.

### `TaskRepository`: `insert` and the int→TaskId boundary on all methods

```python
async def insert(self, new_task: NewTask) -> Task: ...
async def get(self, task_id: TaskId) -> Task | None: ...
async def save(self, task: Task) -> None: ...           # unchanged shape
async def update_status(self, task_id: TaskId, status: TaskStatus) -> None: ...
async def list_ids_by_ip_and_status(self, ip: str, status: TaskStatus) -> list[TaskId]: ...
async def list_by_jobs(self, job_ids: list[TaskId]) -> list[Task]: ...
async def list_by_status(self, statuses: set[TaskStatus], *, limit: int | None = None) -> list[Task]: ...  # unchanged
async def count_by_status(self) -> Mapping[TaskStatus, int]: ...  # unchanged
```

`insert` now takes `NewTask` (not `Task`). It runs `task/insert.sql ... RETURNING
task_id` (already present), reads `rows[0]`, and returns `_row_to_task(rows[0])`
— which wraps `TaskId(int(row["task_id"]))`. Returning the full `Task` (not just
`TaskId`) avoids a second `get` round-trip in `submit_task` and matches the
existing shape.

`get`/`update_status`/`save` pass `task_id.value` to SQL (pg8000 can't adapt a
dataclass). `list_ids_by_ip_and_status` returns
`[TaskId(int(row["task_id"])) for row in rows]`. `list_by_jobs` takes
`list[TaskId]` and passes `[tid.value for tid in job_ids]` as the SQL param
(`list_by_jobs.sql` uses `= ANY(:task_ids)`; the adapter adapts a list of ints).

`save`, `list_by_status`, and `count_by_status` are unchanged in signature
(they take/return `Task` / mappings, which carry `TaskId` internally). The
`save(task)` body passes `task.task_id.value` to `update_by_id.sql`.

The batch APIs (`list_ids_by_ip_and_status`, `list_by_jobs`) were initially
considered for an "int carve-out" (keeping them `int` to avoid touching
`yasetnode`'s loop and the facade's input). Rejected: `list_ids_by_ip_and_status`
feeds `update_status(task_id: TaskId)` in `yasetnode`, so keeping its return
`list[int]` would force a `TaskId(i)` wrap in the CLI loop; and `list_by_jobs` is
driven by the facade, which is already the marshalling boundary. So **all**
repository methods take/return `TaskId`, and the facade is the sole `int`
boundary — the cleanest end-to-end story, with no carve-out exceptions to
remember.

### Use cases: `submit_task` returns `TaskId`; entry points take `TaskId`

```
submit_task:
    new_task = NewTask(label=label, context=context)   # status/allocated_ip default
    task = await uow.tasks.insert(new_task)            # Task, task_id assigned here
    ... with_context(remote_folder based on task.task_id) ...
    ... with_event(TaskCreated, ...) ...
    await uow.tasks.save(task)
    return task.task_id                                # TaskId (was int)
```

`allocate_task(task_id: TaskId, ...)` and `consume_task(task_id: TaskId, ...)`
take `TaskId` (was `int`). They call `uow.tasks.get(task_id)` (now `TaskId`);
logging `"task_id=%s"` renders via `__str__`; `tracker.add`/`discard(task_id)`
keys become `TaskId`. `query_tasks(jobs: Sequence[TaskId] | None, ...)` forwards
`list(jobs)` to `list_by_jobs(list[TaskId])`.

The orchestrator reads task ids from `list_by_status -> [Task]` (each carries
`TaskId`) and feeds `allocate_task`/`consume_task` — so `TaskId` flows
end-to-end internally, with **no conversion** at the orchestrator/use-case
boundary. `AllocationTracker`'s internal `set` becomes `set[TaskId]` (the
tracker never crosses the public boundary; its spec scenarios update
`42 -> TaskId(42)`).

### The `Yascheduler` facade: the sole `int`/`TaskId` boundary

The public `Yascheduler` facade signatures are FROZEN
(`package-facades` spec: "Yascheduler client query method public contract"):

- `queue_submit_task(...) -> int` — stays `int`. Wraps `submit_task` and returns
  `(await submit_task(...)).value`.
- `queue_get_task(task_id: int)` / `queue_get_task_async(task_id: int)` — stay
  `int`-typed. Internally wrap `TaskId(task_id)` before calling
  `uow.tasks.get(TaskId(...))` (or `list_by_jobs([TaskId(task_id)])`).
- `queue_get_tasks(jobs, status)` / `queue_get_tasks_async(jobs, status)` —
  `jobs` stays `list[int]`. Internally wrap `[TaskId(i) for i in jobs]` before
  calling `query_tasks(jobs=[TaskId(...)], ...)`.
- The returned dict (built by `_task_to_dict`) keeps `task_id` as `int`:
  `"task_id": t.task_id.value`.

The facade is the **sole** int/TaskId marshalling layer — one place to audit, in
both directions (input wrap `TaskId(int)`, output extract `.value`). This is the
Scope B boundary story: the domain is type-safe, the public API is stable, and
the conversion is centralized.

### No migration, no SQL changes

Unlike `add-node-id-identity`, this change touches no SQL and no migration:
`yascheduler_tasks.task_id SERIAL PRIMARY KEY` and `task/insert.sql ...
RETURNING task_id` already exist. This is the key simplification — the entire
change is domain (`model.py`, `events.py`, `exceptions.py`), ports (`ports.py`),
two infra adapters (`postgres.py`, `persistence/exceptions.py`,
`notifier/webhook.py`), use cases (`submit_task.py`, `allocate_task.py`,
`consume_task.py`, `query_tasks.py`, `allocation_tracker.py`), the facade
(`client.py`), and CLIs (`check_status.py`, `show_nodes.py`, `submit.py`). Plus
tests.

### `yastatus`, AiiDA plugin, `_events`: explicit non-goals

- The public `Yascheduler` facade signatures do NOT change (frozen). The
  `int`/`TaskId` conversion is internal to the facade.
- The AiiDA scheduler plugin (`entrypoints/aiida_plugin.py`) consumes the
  facade's `int`-typed API (`queue_get_task(task_id: int)`,
  `queue_get_tasks(jobs=[int])`) and is unaffected — no `TaskId` reaches it.
- The `_events: tuple[DomainEvent, ...]` transient-field design on `Task` is
  unchanged. `NewTask` carries no `_events` (events are collected on the
  persisted `Task`), but this is a consequence of the split, not a redesign of
  the event-collection mechanism.
- Node-side identity (`NodeId`, `MachineSession.node_id`, `ConnectedMachine`) is
  the `add-node-id-identity` change's territory and is not touched here. The two
  changes are independent (different entities) but both modify `domain/model.py`
  and the `domain-entities` spec; whoever lands second reflows the other's line
  numbers (trivial), and the spec deltas compose (different entities, no
  conflict).
