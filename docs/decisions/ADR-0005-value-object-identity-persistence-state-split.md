# ADR-0005: Value-object identity with persistence-state split

- **Status:** Accepted
- **Date:** 2026-07-03
- **Supersedes:**
- **Superseded by:**

## Context

The codebase used bare `int` for every entity identity — `task_id: int` and `ip:
str` as the de-facto node key — with no type-level distinction between pre- and
post-persistence. `Task(task_id=0, ...)` was a load-bearing sentinel: `insert`
ignored `task_id`, the DB generated the real value, and every consumer silently
accepted `0` meaning "not real yet". `Node` had no stable PK at all; `ip
VARCHAR(15) UNIQUE` served as identity everywhere, including as a nullable
placeholder (`'prov'||MD5(...)`) for temp cloud nodes.

## Decision

Use `@dataclass(frozen=True)` value objects (`NodeId`, `TaskId`) for all entity
identities, with a type-state split (`NewNode`/`Node`, `NewTask`/`Task`) to
express pre- vs post-persistence at the type level. Use `GENERATED ALWAYS AS
IDENTITY` for DB primary key generation. Adopt Scope B for `TaskId` propagation
(end-to-end inside the domain, facade as sole `int` boundary).

## Alternatives Considered

### `typing.NewType` or `int` subclass vs frozen dataclass

A frozen dataclass was chosen because `NewType` erases to `int` at runtime (no
boundary guard, no validation, no methods) and an `int` subclass defeats
value-object ergonomics (mixing remains possible, `__post_init__` is
non-trivial). The dataclass enforces explicit `.value` unwrapping at every
external boundary — pg8000 params, JSON serialization, argparse — and supports
`__post_init__` for positive-value enforcement and `__str__` for ergonomic
CLI/logging rendering.

### Nullable `id` vs type-state split

A nullable `id: int | None` on a single class was rejected because it forces
every consumer to handle `None`, relying on runtime discipline rather than the
type system. The `NewNode`/`Node` and `NewTask`/`Task` split makes "don't
construct an entity without a real id" structural: the pre-persistence form has
no identity field, the post-persistence form requires it. `NewNode` → `Node` and
`NewTask` → `Task` conversion happens in exactly one place — `Repository.insert`
— making identity-enforcement verifiable by inspection.

### `SERIAL` / `GENERATED BY DEFAULT` vs `GENERATED ALWAYS`

`SERIAL` and `GENERATED BY DEFAULT` both accept explicit PK inserts silently.
`GENERATED ALWAYS AS IDENTITY` is the SQL:2003 standard idiom that binds the
sequence to the column and rejects explicit inserts (without `OVERRIDING SYSTEM
VALUE`). Since the application never inserts PKs explicitly, `ALWAYS` adds a
real guard against future bugs at no runtime cost. Migration from `SERIAL`
requires PG12+ (satisfied: testcontainer is PG16, no PG10-11 target exists). The
migration drops old SERIAL sequences and recreates identity sequences, seeding
them above current `MAX(id)`.

### Scope A vs Scope B for TaskId propagation

Scope B was chosen over Scope A because Scope A would require `.value`
extraction at every event construction site (`Task.with_event` calls all 5
subclasses) and every exception constructor, scattering unwrap logic across the
domain. Scope B keeps `TaskId` end-to-end inside the domain — events carry
`TaskId`, exceptions store `TaskId`, every `TaskRepository` method takes/returns
`TaskId` — with the facade as the single `int`/`TaskId` marshalling layer in
both directions (input wrap `TaskId(int)`, output extract `.value`).

## Consequences

- **Positive:**
  - Identity is type-safe: mixing a `NodeId` with a bare `int` (or with a
    `TaskId`) is a type error at the call site, not a runtime surprise.
  - Persistence state is explicit: a `NewNode` cannot be passed where a `Node`
    is expected; the compiler/enforcer catches it.
  - `GENERATED ALWAYS` rejects explicit PK inserts — a loud PG error rather than
    silent corruption.
  - The type-state split eliminated the `task_id=0` sentinel and the
    `ip`-as-fake-id placeholder.
  - Scope B centralized `int`↔`TaskId` marshalling in the facade — one place to
    audit.
- **Negative / trade-offs:**
  - Every external boundary (pg8000 params, JSON, argparse) must unwrap `.value`
    explicitly — this is the intentional cost of type safety, but it means new
    adapters cannot forget the unwrap without a runtime crash.
  - The `NewNode`/`Node` and `NewTask`/`Task` duality adds two extra dataclass
    definitions per entity. `NewNode` and `NewTask` must be kept in sync with
    their post-persistence counterparts.
  - `NodeId`/`TaskId` are not drop-in replacements for `int`: `NodeId(5) == 5`
    is `False`, so callers cannot accidentally mix them — but this also means
    utility code (sorting, hashing in mixed-int contexts) must be mindful.
  - The SERIAL→GENERATED ALWAYS migration is not idempotent and requires careful
    sequencing (drop old sequence, create identity sequence, seed via `setval`).
- **Accepted risks:**
  - The type-state split increases the number of classes, but the pattern is
    mechanical and the conversion point is singular (`Repository.insert`),
    making it low-maintenance.
  - The `GENERATED ALWAYS` guard breaks any future code that inserts PKs
    explicitly — this is the intended protection; the failure is loud and
    immediate.
  - The `ip`-keyed mutators (`WHERE ip =`) remain unchanged for nodes; switching
    to `WHERE node_id =` is deferred to a future change. Existing ip-based
    identification coexists with `NodeId`-based identification without conflict.
